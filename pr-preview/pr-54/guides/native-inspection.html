Inspect Native macOS UI ​

What it does ​

Recon can inspect a running macOS application's AppKit windows, views, cells, layers, layout, and observed fonts. ui view reads native objects through a Recon helper in the selected process. ui ax tree reads the separate Accessibility representation; ui windows reads WindowServer windows; ui screenshot captures pixels. An accessible control may correspond to several native objects, or to none that Recon can observe. ui correlate compares separate native and AX observations without turning a possible match into a shared identity.

Native inspection requires an explicit ui session. External AX, window enumeration, and screenshot capture still work without one. The former AX command recon ui tree is rejected, including when given --session; replace it with recon ui ax tree. There is no top-level ax command or automatic AX-to-native fallback. Use recon schema ui ax tree, recon schema ui view tree, and the recon ui session --help group to inspect the installed command contract.

How to use it ​

Check the target and your permissions ​

Native inspection supports Apple silicon on macOS 27, including compatible arm64e targets under the research profile. Intel and Rosetta-translated processes, older macOS, UIKit/Catalyst, Simulator, and iOS devices are outside this capability. Choose an exact application name, bundle identifier, or absolute .app path. Recon resolves that bundle and selects its running instance. Without a session, pass --pid PID when several instances belong to the same bundle; preflight returns AMBIGUOUS_INSTANCE if several are running and none is selected. With --session SESSION, Recon selects the session's bound process even when several instances run, and any supplied --pid must match or the command returns STALE_SESSION. The session must belong to the same bundle at the same location. A bare PID or executable path does not bypass bundle selection. A restarted application needs a new session even if macOS reuses its PID.

Start with recon context to check Recon's own privacy grants, and recon ui session preflight TARGET [--pid PID] to inspect target-specific session eligibility. Neither requests a grant, loads code, starts the app, or changes host security. Preflight reports bundle/process/architecture facts, observed signing and protection facts, and eligible, blocked, or unknown per mode/profile with reasons and evidence sources. Its helper.standard and helper.research facts describe the artifacts each profile would use when opening: research prefers the installed /Library/Application Support/Recon pair, then follows the normal packaged-artifact search. A helper build-id file and a loader on disk establish availability, not compatibility with a running target. Without authenticated build and protocol evidence, compatibility remains unknown. An inaccessible fact is unknown rather than false. A successful report may show every mode blocked; eligibility does not guarantee that a later open succeeds. An ambiguous or unresolvable target still fails under the normal selection contract. Preflight assesses inspection access, not Screen Recording or Accessibility readiness for every other ui command.

External ui windows needs Recon's Screen Recording grant, ui ax tree needs Accessibility, and ui screenshot needs Screen Recording plus Accessibility when --window is omitted and it must find the main window. ui correlate needs an external AX observation, so it needs Recon's Accessibility grant; a loaded helper cannot supply that host-side grant. See Observe macOS Application UI for signing and granting Recon's privacy identity. A required missing grant on an existing UI path may trigger a macOS setup dialog and then return PERMISSION_DENIED. context and session preflight never prompt. Establish grants before depending on uninterrupted observation.

Choose a session mode and profile ​

The syntax is recon ui session open TARGET --mode existing|launch|attach [--profile standard|research] [--pid PID] [--allow-authorization]. Specify a mode; there is no default or automatic fallback. standard is the default profile. Use the mode matching the state of the exact target:

ModeEffect and prerequisite
existingConnect to a compatible Recon helper already resident in the selected running process. It does not load another image. An inactive resident helper can establish a fresh session.
launchStart the selected app in the background with the helper enabled, only when it is not running. It refuses an already-running app instead of activating or replacing it. --pid is invalid. This is an explicit application-launch effect; after background startup, Recon uses its process-bound loader, not a DYLD environment variable.
attachLoad the helper into the selected running process without relaunching or quitting it. This executes target-side code and is subject to that process's protections.

standard uses existing cooperation, signing, and debugger permissions without preparing the host. A cooperative hardened target does not need the allow-dyld-environment-variables entitlement for background launch through the bound loader; it still needs compatible architecture, signing, and helper support. A protected target without cooperation does not become standard-eligible through that launch route. Attaching to a non-cooperative third-party app or a first-party/platform binary requires research; standard and an unprepared host reject those attempts with a named access prerequisite. Research is an operator-prepared machine profile, not a promise of access to any installed app. First-party inspection is injection-only; there is no read-only external-memory fallback. On the research path a protected first-party/platform binary requires SIP and AMFI disabled and a Recon inspector signed with com.apple.private.thread-set-state; the kernel honors that entitlement only with AMFI off. This is a research-only, non-shippable host posture. Signing, library validation, architecture, and target protections may still prevent a particular attempt. Recon does not re-sign target apps or grant itself access.

An attach mechanism that could request macOS debugger authorization must disclose that in preflight. Only --mode attach --allow-authorization permits that mechanism's authorization interaction; without the flag Recon must refuse rather than show the dialog. Using the flag with existing or launch is a usage error. The operator, not Recon, decides whether to approve a dialog and enters any credentials. Denial does not trigger another mechanism, identity, or escalation.

Opening succeeds only after an authenticated target-side handshake and bounded identity read. The result identifies the exact bundle and process incarnation, OS/build, target architecture, session identifier, requested mode and actual acquisition history, profile, helper build and protocol, capabilities, and effects. existing or attach can return reused: true for a compatible active session without another injection; a conflicting profile or helper build fails. Only one Recon inspection session may be active in a process at a time. Install matching Recon CLI and helper builds: protocol/build mismatches fail rather than replacing resident helper code or silently downgrading.

Sessions use a local-only, owner-private bootstrap and authenticated, unguessable session access. The bootstrap may remain available after session close but cannot read UI objects without an active session. Do not share a session identifier or owner-private recovery files as if they were transferable credentials. This boundary rejects wrong-process and cross-session requests but does not promise isolation against a same-user process capable of reading the owner's files or memory. No network service or arbitrary-method execution API is part of the helper.

Prepare a research host only if you own and authorize it ​

Host preparation deliberately weakens macOS security for research. Never do this on an ordinary workstation merely to make an inspection command succeed. recon ui session prepare-host --status reports SIP, AMFI, and boot-argument prerequisites and missing facts without changing them. The separate recon ui session prepare-host command discloses the exact changes, requires confirmation, and uses sudo nvram to set the boot arguments it can set: amfi_get_out_of_my_way=0x1 -arm64e_preview_abi tss_should_crash=0. Reboot for the changes to take effect. This command is never invoked implicitly by preflight, open, or a read. It cannot disable SIP itself.

On an authorized Apple-silicon research Mac, the operator disables SIP in Recovery:

  1. Save work and shut down the Mac. Press and hold the power button until startup options appear, choose Options, then Continue. Authenticate with an administrator account if Recovery asks.
  2. In Recovery, open Utilities → Terminal, run csrutil disable, and follow its on-screen instructions. Restart the Mac. This step must be done by the operator in Recovery, not by Recon or a normal macOS shell.
  3. Back in macOS, check recon ui session prepare-host --status. If you choose to apply the AMFI-off boot arguments, run recon ui session prepare-host, review its disclosure, confirm the sudo nvram operation, reboot, and check status again before attempting research access.

recon ui session prepare-host --revert removes only Recon-set boot arguments. A successful change instructs a reboot; when there is no Recon ownership record or boot-argument change, the result reports changed: false and rebootRequired: false. Revert does not turn SIP back on. To restore SIP yourself, return to Recovery by the same startup-options route, run csrutil enable in Utilities → Terminal, and restart. Check the state afterward. Neither revert nor session close reverses changes someone else made to the host. Ordinary inspection, session open, and session close do not run sudo, disable protections, change TCC grants, install a privileged service, or edit another app's signature.

If the boot-argument change succeeds but Recon cannot save which arguments it added, preparation reports an error. The host may have changed, and prepare-host --revert cannot safely remove unrecorded arguments. Inspect the configured boot arguments with prepare-host --status and remove only the arguments you authorized manually; another prepare-host run cannot recover their original ownership.

After you confirm preparation, Recon rereads the current boot arguments and its ownership record before changing either. If the boot-argument plan differs from what it disclosed, it stops before sudo; rerun the command to review and confirm the new plan. Concurrent Recon apply and revert commands take turns through the ownership update, so a revert cannot remove a record while an apply is acting on the old one. If Recon cannot acquire its owner-private host-preparation lock, it returns INSPECTION_UNAVAILABLE without making the requested host change. --status remains read-only and does not wait for that lock. Other NVRAM editors do not participate in this coordination; inspect the host state if another tool or operator may have changed it during preparation or revert.

If revert cannot clear its ownership record, it stops before changing boot arguments. If it clears the record but cannot change boot arguments, it reports an error and requires manual inspection; it cannot safely retry the old ownership decision.

Inspect a selected process ​

The command shapes below use TARGET for the selected bundle, SESSION for the identifier returned by open, ID for a current WindowServer CGWindowID returned by ui windows, and HANDLE for an opaque native handle returned by a session-backed result. Replace these metavariables with actual values from your own results; they are not literal arguments or durable identifiers.

CommandResult and scope
recon ui windows TARGET [--pid PID] [--session SESSION]Without a session, the usual WindowServer windows array. With one, also bounded nativeWindows for AppKit windows/panels, child-window/sheet relationships, session/provenance, and coverage. Native window numbers are source-specific; a usable windowId requires verified live WindowServer mapping.
`recon ui view tree TARGET --session SESSION [--pid PID] [--window ID] [--root HANDLE] [--kind viewlayer] [--depth N] [--fields LIST] [--limit N]`
recon ui view node TARGET HANDLE --session SESSION [--pid PID] [--fields LIST]Reads one live native window, view, layer, cell, or layout guide with its actual kind. Related objects are references, not an expanded subtree.
`recon ui view find TARGET --session SESSION [--pid PID] [--window ID] [--root HANDLE] [--kind viewlayer] [--class NAME] [--identifier TEXT] [--depth N] [--fields LIST] [--limit N]`
recon ui view fonts TARGET --session SESSION [--pid PID] [--window ID] [--root HANDLE] [--depth N] [--limit N]Inventory of font descriptors actually observed in the selected scope, with source kinds, contributing handles, and coverage. Bounded attributed-text runs do not export text content.
recon ui ax tree TARGET [--pid PID] [--window ID] [--depth N] [--no-menu-bar] [--session SESSION]The external AX tree with its existing depth, menu, and window rules. Optional session binds the process; it does not run the native walker.
recon ui screenshot TARGET [--pid PID] [--window ID] --out FILE [--session SESSION]Save one WindowServer window to a new PNG file through the existing capture path. An existing output path is an error. Optional session binds the process without injection.
recon ui correlate TARGET --session SESSION --window ID [--pid PID] [--depth N] [--limit N]Collect separate live native and external AX observations of that window and report evidence-backed candidate matches, independent timestamps, and coverage.

--window is always a WindowServer ID belonging to the selected process, never an AppKit window-device number or native handle. Native queries resolve it to the live window; no title, position, or frontmost-window guess is used. A native-only window without a verified WindowServer ID can be inspected by its returned native handle. An unmatched or hidden/closed-but-retained window can lack a usable mapping; native matching reports unavailability rather than inventing an ID. Session-bound AX and capture still use their own external window selection and do not require a native match. If both --window and --root are supplied, the live root must belong to that window; moving it elsewhere invalidates that scoped request.

View tree/find and fonts accept a native window or view root. Layer tree/find require a native window, view, or layer root, or a --window whose content view has an existing layer. A missing content view or associated layer produces a reported absent relationship and an empty layer scope. An incompatible root kind is INVALID_ARGUMENT. Cells, masks, and layout guides are typed relationships, not fabricated view children; model layers form a separate graph. A SwiftUI hosting boundary may be identified, but SwiftUI values and modifiers are not reconstructed. No read forces a view, backing layer, layout, or redraw into existence.

--fields LIST is a nonempty comma-separated set: basic (default: runtime class, identity, geometry, coordinate orientation, hidden/alpha state, child counts), appearance (appearance, supported colors, visual-effect properties), font (carrier, descriptors, traits, size, bounded attributed runs), layout (held/touching constraints, owner/items, intrinsic size, hugging and compression), layer (existing associated model layer and supported geometry/appearance), and cell (existing control cell and supported state/font). Unknown or repeated groups are usage errors. Identity, kinds, necessary relationships, and completeness metadata appear independently of field selection. Per-field statuses distinguish absent, unsupported, denied, failed, and non-finite values; an unrequested field simply is not fetched. A zero or false value is real data. Frames retain AppKit logical-point coordinate spaces and orientation, with window/screen normalization only where computable. layerState: model does not describe current animated presentation.

Native tree/find/fonts default to depth 3 and 200 returned records. Depth can be 0 through 64; limit 1 through 25,000. The selected root is depth zero, including each content root in a window forest. The helper also caps work at 25,000 visited objects/relationships per request, at most 256 attributed runs per carrier, 64 KiB per request, 8 MiB per full response, and 4,096 Unicode scalars per returned string with truncation marked. Requested narrowing and uncompleted work have separate narrowed and truncated reasons; a partial font inventory or find result never claims exhaustive coverage. An empty fully observed scope differs from an unavailable one. Native observation provenance names the process incarnation, session/helper/protocol, native-appkit source, requested scope/fields, observation ID, start/end times, OS/build/architecture, and coverage. Main-thread observation over that interval is best-effort, not an atomic snapshot of the app or pixels.

Correlation requires a real shared window mapping and external AX permission. A nonempty exact accessibility identifier on both sides can support a candidate; otherwise the candidate needs matching self-reported AX role and screen bounds within one logical point on every edge. Recon retains ambiguous candidates and records the matching basis. A native view identifier is not silently treated as its accessibility identifier. A unique candidate is still evidence, not proof of object equality or an executable action target. Missing AX evidence fails correlation with its typed cause, without disabling separate native inspection.

Worked example ​

Use an app you own or are authorized to inspect. Replace /absolute/path/to/YourApp.app with its actual absolute bundle path; these commands do not assume it is running or eligible. The first two only report facts:

sh
APP=/absolute/path/to/YourApp.app
recon context
recon ui session preflight "$APP"

If preflight supports an already-present compatible helper in a running instance, open explicitly without loading a new helper image:

sh
recon ui session open "$APP" --mode existing

Read the actual session identifier from that command's JSON and set SESSION to it in your shell. The guard below prevents a blank session value from being used. Only run the reads if opening succeeded; choose the --window ID and native handles from your own ui windows and ui view results, never from an earlier process incarnation.

sh
: "${SESSION:?Set SESSION to the identifier returned by open}"
recon ui windows "$APP" --session "$SESSION"
recon ui view tree "$APP" --session "$SESSION" --depth 2 --fields basic
recon ui session close "$SESSION"

For a verified WindowServer ID, the corresponding commands are recon ui view tree "$APP" --session "$SESSION" --window "$WINDOW", recon ui ax tree "$APP" --session "$SESSION" --window "$WINDOW", recon ui correlate "$APP" --session "$SESSION" --window "$WINDOW", and recon ui screenshot "$APP" --session "$SESSION" --window "$WINDOW" --out /absolute/path/to/new-inspection.png. Set WINDOW from the actual window list first, use a path that does not exist for the PNG, and run these before closing the session. The screenshot writes a file; none of these commands is guaranteed to succeed for every window or privacy configuration.

Limits and edge cases ​

  • Native operations run allowlisted AppKit reads on the target's main thread. A getter override can execute application code, hang, change UI or focus, or crash the target even though Recon requests observation only. Loading a helper and background --mode launch also have distinct target-side effects. External AX and capture have their own effects and permission contracts. Inspection is not arbitrary method invocation, text extraction, or a guarantee that target code is pure.
  • Once required setup is complete, ui must not activate/raise a target, make its window key, switch Spaces, move the real pointer, or redirect input. No activate-then-restore or focus-without-raise fallback is allowed. A known unsafe mechanism is unavailable; detected interference is UI_INTERFERENCE, with observed effects reported and no automatic focus restoration or retry. The retained privacy-permission request and explicitly allowed attach debugger dialog are setup exceptions and can interrupt the desktop; they do not excuse target activation, Space switches, pointer movement, or redirected input. recon app launch separately has an explicitly activating behavior; session --mode launch requests background startup.
  • If a ui operation fails and Recon also observes focus or input interference, it reports UI_INTERFERENCE with both the observed disturbance and the underlying failure message. A failed operation never hides observed interference.
  • A native read has a two-second deadline across queue, execution, transport, and delivery; open/close have ten seconds. An expired queued read must not start later. A getter already executing may continue after INSPECTION_TIMEOUT, so the error can report its stage and targetExecutionMayContinue: true. Recon cannot unwind it safely. Only one helper UI read per process may be outstanding; subsequent native reads are INSPECTION_BUSY until unresolved execution finishes or the process exits, even if you close and reopen. Session binding does not put external AX/capture in this queue.
  • Handles are weak, opaque identities within one session. Reordering or reparenting preserves a surviving object's handle, but deallocation/replacement, close/reopen, exit, or relaunch makes the old identity stale. A moved object can also fail a former window-scoped query. Do not store a structural path, pointer, title, frame, AX path, or window number as a replacement identity. Registry capacity is 100,000 live handles; exhaustion is reported as unavailable capacity, not silent eviction. Copied observations remain historical JSON, not live handles.
  • recon ui session close SESSION revokes the capability and handles, and leaves the application running. The helper and owner-private bootstrap may stay resident until process exit; the close result reports that separately from session state. An acknowledged close and an already-closed locally known session are distinct successes. If the transport fails or acknowledgment is missing, the session remains close-unconfirmed locally and close exits nonzero with a typed error on stderr, without success JSON. Repeat close for that session or explicitly open for that same process to reconcile through authenticated bootstrap state. While unresolved, Recon refuses native reads and replacement injection; if the old session is still active, open returns INSPECTION_BUSY with recovery action. An unreachable bootstrap preserves the unknown outcome. Quit or restart only an application instance you own and intend to stop; closing inspection never quits it.
  • A second concurrent open for the same process returns INSPECTION_BUSY. If the CLI crashes during attach and a helper may have loaded but cannot be authenticated, Recon refuses another injection until authenticated bootstrap reconciliation or confirmed target exit. Missing local records do not prove the attach had no effect.
  • Failures use one typed JSON error on stderr, no success JSON, and a nonzero exit status. INVALID_ARGUMENT covers malformed options, handles, or incompatible scope; STALE_SESSION and STALE_NODE cover well-formed expired identities. INSPECTION_UNAVAILABLE reports unsupported architecture/build and missing access prerequisites; INSPECTION_PROTOCOL_MISMATCH reports incompatible helper/protocol; INSPECTION_FAILED reports native failures; INSPECTION_TIMEOUT, INSPECTION_BUSY, and UI_INTERFERENCE describe uncertain execution, contention, and observed focus effects. Details identify stage, cause, and remaining execution/helper residency where known. A failed attach or uncertain timeout is not automatically safe to retry. External AX/capture retain their own permission, interface, and timeout errors instead of fabricating a native-session requirement.
